# Reliable Tool Calling: Schemas, Validation, Retry and Structured Outputs

## 1. Scenario

For this task, I created a **College Student Assistant** using an OpenAI-compatible API.

The assistant helps a college student with two simple operations:

1. Calculate attendance percentage.
2. Retrieve information about a college subject.

The first tool is `calculate_attendance`. It accepts the number of present classes and total classes and calculates the attendance percentage.

The second tool is `get_subject_info`. It accepts a subject name and class type and returns information such as faculty, room and subject type.

The model does not directly execute these functions. The model generates a tool call, and my Python program validates and executes the requested function.

---

# 2. Chat Completions Format

The Chat Completions API uses messages to represent the conversation between the user, the assistant and tools.

The main request fields used in my project are:

* `model` – specifies the model to use.
* `messages` – contains the conversation.
* `tools` – describes the functions available to the model.
* `tool_choice` – controls whether the model can select a tool.
* `max_tokens` – limits the generated response.

A response contains information such as:

* `choices`
* `message`
* `content`
* `tool_calls`
* `finish_reason`

The `finish_reason` tells my program why the model stopped generating.

### `stop`

This means the model has completed its normal response. My program can return the answer to the user.

### `length`

This means the response was stopped because it reached the token limit. My program retries the request with a larger `max_tokens` value.

### `tool_calls`

This means the model wants my program to execute one or more tools.

When the model wants to call a tool, `message.content` can be empty because the useful information is inside `message.tool_calls`.

# 3. OpenAI-Compatible Server

An OpenAI-compatible server provides an API that follows the same general request and response format used by the OpenAI Python client.

Because of this compatibility, the same client library can communicate with different providers by changing the API key and `base_url`.

In my project, I used the OpenAI Python library and changed the base URL to my provider's OpenAI-compatible endpoint.

However, "OpenAI-compatible" does not guarantee that every provider supports every OpenAI feature. For example, some providers may not support a particular structured-output feature or may implement tool calling differently.

---

# 4. Streaming

Streaming means receiving the model's response in smaller pieces instead of waiting for the complete response.

For example, instead of waiting for:

`Your attendance is 84%.`

the application may receive:

`Your` → `attendance` → `is` → `84%`.

Streaming improves responsiveness because the user can see the response while it is being generated.

I did not use streaming in my agent because an agent loop must carefully process tool calls, validate them, execute them and send the results back to the model. Handling complete responses makes this workflow simpler for this task.

The Responses API uses a different interaction style from Chat Completions. This task uses Chat Completions because the assignment specifically focuses on the Chat Completions tool-calling workflow.

# 5. Five Steps of a Tool Call

My tool-calling process follows these steps:

### Step 1 – Send the request

My Python program sends the user's message together with the available tool definitions.

### Step 2 – Model requests a tool

The model decides that it needs a tool and generates a tool call containing the function name and arguments.

### Step 3 – Parse and validate

My Python program parses the generated JSON arguments and checks whether the requested tool exists and whether its arguments match the schema.

### Step 4 – Execute

If validation succeeds, my Python program executes the actual Python function.

The model does not execute the function.

### Step 5 – Return the result

The function result is sent back to the model as a tool message. The model can then use that result to produce the final answer.

This is important because the tool call is generated by the model. Therefore, my program cannot blindly trust the generated arguments.

# 6. Tool Definition and Schema

My tools use JSON Schema to describe their expected arguments.

The important schema fields are:

### `description`

Explains what the tool or argument is used for.

### `properties`

Defines the available arguments and their data types.

### `required`

Specifies arguments that must be present.

For example, `calculate_attendance` requires both:

* `present_classes`
* `total_classes`

### `enum`

Restricts an argument to a fixed set of values.

For `get_subject_info`, the class type can only be:

* `theory`
* `lab`

### `additionalProperties`

I set this to `false`.

This prevents the model from adding unexpected arguments such as:

`college: "BIT"`

### `strict`

Strict schema mode makes the expected output structure more restrictive when supported by the provider.

---

# 7. Tool Choice

The main `tool_choice` options are:

### `auto`

The model decides whether to call a tool.

I use this for my student assistant because some questions require tools while others do not.

### `none`

The model is not allowed to call tools.

### `required`

The model must call a tool.

### Named function

The application can force a particular function to be called.

For my scenario, `auto` is the most suitable choice because the assistant should decide whether the student's question requires a tool.
